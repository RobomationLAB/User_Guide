# 번역 가이드

`ko` 를 기준으로 다른 언어를 번역할 때 지켜야 하는 규칙.

> 이 파일은 `srcDir`(`docs/pages/`) 밖에 있어 사이트로 빌드되지 않는다.

## 구조

21개 언어 = `ko`(원본) + `en` + 나머지 19개. **`ko` 가 원문이고 `en` 이 용어 기준이다.**

```
docs/
  pages/            ← srcDir. URL 에 'pages' 는 나타나지 않는다
    ko/  en/  …     ← 21개 언어
      index.md
      guide/  program/  common/  roboids/  AI/  CheeseStick/
  public/images/    ← <언어>/<카테고리>/<모듈>/<id>.png
```

한 언어는 문서 45개다 — 
`index.md` + `guide` 2 + `program` 3 + `common` 11 + `roboids` 7 + `AI` 10 + `CheeseStick` 11.

이미지는 언어당 블록 465장(+ `_manifest.json` 39개) + 앱 UI 스크린샷 63장이다.
문서가 `<BlockImage>` 로 참조하는 고유 조합은 **523개**(블록 461 + 앱 UI 62)다.

참조되지 않는 실물이 5장 있는데 의도된 것이다 —
`common/control/wait_input`, `common/functions/procedures_callreturn`, `common/logic/logic_null`, `common/loops/controls_repeat_ext` `program/Menu/toolbar.png`.
`check:i18n` ④ 는 *참조 → 실물* 방향만 보므로 반대 방향(안 쓰이는 실물)은 걸리지 않는다.

> **어디까지 됐는지는 이 파일에 적지 않는다.** 
> `npm run check:i18n` 이 언어별로 문서 수 · 미번역 수 · 미착수 여부를 그때그때 계산해서 보여준다.
> 진행 상황을 문서에 옮겨 적으면 기준이 둘이 되고, 낡은 쪽을 근거로 잘못 판단하게 된다.

## 규칙 1 — 절대 번역하지 않을 요소들

### ① 디렉터리·파일명: 대소문자까지 `ko` 와 동일

`docs/pages/en/common/Logic.md` 처럼 정확히 같아야 한다. `config.js` 의 `CATEGORIES`
items 와 문자열이 일치할 때만 사이드바에 나타나고, `buildSidebar` 가 `readdirSync` 로
**대소문자를 정확히 대조**한다.

macOS 는 파일시스템이 대소문자를 구분하지 않아 오타가 로컬에서는 통과하고
**Linux 빌드에서만 깨진다.** `npm run check:i18n` 이 이걸 잡는다.

### ② 제목 앵커 `{#id}`: `ko` 와 100% 동일

다국어 문서의 근간이다. 현재 `ko` 앵커는 전부 ASCII 이므로 그대로 복사한다.

```md
## 조건문 (만약 ~ 라면) {#controls_if}     ← ko
## If statement {#controls_if}             ← en, 앵커는 그대로
```

앵커를 번역하면 언어마다 달라져 문서 간 링크가 언어별로 깨진다.
**`{#id}` 를 생략하는 것도 안 된다** — VitePress 가 제목 텍스트로 자동 생성하는데
한글은 NFD(자모 분해)로 나와 손으로 쓴 링크와 문자열이 일치하지 않는다.

또한 **모든 `##` 에는 명시적 `{#id}` 가 있어야 한다.** 사이드바가 `##` 목록을
하위 항목으로 넣는데, `readHeadings` 가 명시적 id 가 있는 것만 대상으로 한다.
id 가 없으면 그 섹션은 사이드바에 나타나지 않는다.

`h1` 에 앵커가 없으면 제목 텍스트에서 id 가 자동 생성된다. **번역한 h1 의 slug 이
같은 문서의 명시 앵커와 겹치면 빌드가 실패하므로 주의한다** — ko 는 h1 자동 id 가
한글(NFD)이라 드러나지 않고 번역 시점에 나타난다. 겹치면 h1 에 명시적 앵커를 준다.

### ③ 문서 간 링크 경로

전부 경로 기반이라 번역 대상이 아니다. 앵커가 붙은 것도 그대로.

```
](Loops)              같은 디렉터리
](../common/Audio)    상위 경유
](AI/ASR)             index.md 에서 하위로
](Menu#robot)         다른 문서의 앵커
```

### ④ `<BlockImage>` 의 모든 속성

```md
<BlockImage module="common/logic" id="controls_if" />
```

`module` 은 **이미지 디렉터리 경로**(소문자 `common/logic`)이고 **문서 파일명**
(`Logic.md`)과 다르다는 점을 주의. `ext` · `inline` · `row` 도 그대로.

### ⑤ `### Python` 소제목

고정 문자열. 모듈 문서마다 3~6회 나온다.

### ⑥ 코드 자체

함수·메서드명과 **API 인자로 의미가 고정된 문자열 리터럴**은 변경 금지.

```python
body_detection.get_distance('left_shoulder', 'right_shoulder', 'horizontal')
```

### ⑦ `index.md` 의 `prev` · `next` 프론트매터

```yaml
prev: false
next: false
```

홈은 목차의 시작점이라 이전/다음 이동 영역을 끈 설정값이다.

## 규칙 2 — 반드시 번역할 요소들

### ① 프론트매터 `title:` — 가장 중요

`buildSidebar` 가 이 값을 읽어 **사이드바 항목 라벨**로 쓴다. 빼먹으면 영어
사이드바에 한국어가 뜬다.

```yaml
---
title: Logic     # ko: 논리
---
```

### ② h1 · 본문 · 제목 텍스트

앵커(`{#id}`)는 규칙 1-② 대로 유지.

### ③ 굵게 강조된 블록 이름 — 문서 전체에서 일관되게, 이미지의 라벨을 따를 것

```md
**그리고** 블록은 …   →   **and** 블록은 …
```

`ko` 문서에 굵게 강조된 고유 용어가 **189개** 있고 대부분 블록·UI 이름이다.
지켜야 할 것은 두 가지다.

1. **같은 블록은 문서 전체에서 같은 이름으로 부른다.**
   `반복` 이 한 문서에서 `repeat`, 다른 문서에서 `loop` 가 되면 문서가 자기
   자신과 모순된다. 이것이 가장 흔하고 가장 고치기 비싼 실수다.
2. **블록 이미지에 라벨이 보이면 그것을 따른다.**
   블록 문서의 `##` 섹션 490개 중 **461개(94%)** 에 `<BlockImage>` 가 붙어
   있고, 그 이미지가 해당 언어의 실제 블록 라벨을 보여준다. 산문의 용어보다
   이미지가 권위 있다.

**`docs/GLOSSARY.md` 가 최종 기준이다.** `ko` 에서 반복되는 표현과 `en` 이 그것을
어떻게 옮겼는지가 정리되어 있다. 번역을 시작하기 전에 읽는다.

용어집에 없는 표현을 새로 정했으면 **작업 보고에 남기고 용어집에 추가한다.**
용어집이 실제 문서와 어긋나면 문서가 아니라 용어집을 고친다 — 기준이 둘이 되면
안 된다.

### ④ 코드 블록 안의 주석

`ko` 기준 29개 파일에 한글 주석이 있다.

```python
# 여러 인스턴스가 있는 경우          ← 20개 파일에 공통
math.sqrt(NUM)  # 제곱근
list.pop(-N)    # 마지막 위치부터 # 번째
```

**코드는 그대로 두고 주석만** 바꾼다.

### ⑤ 예시용 문자열 리터럴

`Utils.speak('안녕하세요')` → `Utils.speak('Hello')`

규칙 1-⑥ 의 API 인자와 구분해야 한다: **화면에 보이는 예시 데이터는 번역,
API 가 해석하는 값은 유지.**

## 규칙 3 — 이미지

**이미지는 번역 대상이 아니다.**  
언어별 실물 파일이 미리 준비되며, 번역자가 만들거나 고칠 것은 없다.  
빠진 것이 있으면 `check:i18n` ④ 가 잡는다.

앱 UI 스크린샷 63장의 구성:

```
images/<언어>/program/Menu/      31개
images/<언어>/program/Editor/    26개 (png 22 + svg 4)
images/<언어>/program/Preview/    6개
```

`guide/` 아래에는 이미지가 없다. `guide/CodingGuide.md` 가 쓰는 setup/loop 블록 구조
그림은 `program/Editor.md` 의 것과 같은 화면이라, **두 문서가
`program/Editor/block-structure` 하나를 공유한다.** 같은 그림을 두 벌 관리하지 않는다.

`program/Editor/` 의 `arrow-right` · `arrow-down` · `circle-empty` · `circle-fill` (svg)은
글자가 없는 도형 아이콘이라 어느 언어에서도 같다. 실제로 21개 언어의 파일이 바이트까지 동일하다 —  
`check:i18n` ④ 가 언어별 실물 파일을 요구하므로 복사본으로 둔다.

### 앱 UI 스크린샷도 언어별로 촬영된 실물이다

**프로그램은 21개 언어로 현지화된다.** (설정 → 언어에서 21개 중 선택)  
그래서 `program/` 스크린샷도 그 언어의 화면이며, **`en` 사본으로 대체해서는 안 된다.**  
`check:i18n` ④ 가 언어별 실물 파일의 존재를 확인한다.

**이미지 누락은 빌드 에러로 잡히지 않는다.**  
`BlockImage` 가 `현재 언어 → en → ko` 로 조용히 폴백하므로, 일본어 페이지에 **영어 스크린샷이 아무 경고 없이 표시된다.  
그래서 누락을 알아차릴 방법은 `check:i18n` ④ 뿐이다.

## 규칙 4 — 검증

```bash
npm run docs:build         # 죽은 문서 링크, 중복 앵커 id
npm run check:i18n         # 전체 언어 요약
npm run check:i18n en      # 특정 언어 상세 (문제가 있으면 exit 1)
```

`docs:build` 가 잡는 것은 **죽은 문서 링크와 중복 앵커 id 뿐**이다.
다음 5가지는 빌드가 잡지 못하므로 `check:i18n` 이 본다:

| | 점검 내용 |
|---|---|
| ① | 파일명 집합이 `ko` 와 동일한가 (대소문자 포함) |
| ② | 앵커 id 집합이 `ko` 와 동일한가 |
| ③ | `](파일#앵커)` 의 앵커가 실제 id 로 해석되는가 — VitePress 는 `#` 뒤를 검증하지 않는다 |
| ④ | `BlockImage` 의 `module`/`id` 조합이 `images/<언어>/` 에 실제로 있는가 (폴백이 감춤) |
| ⑤ | 번역 누락 한글이 남아 있는가 |

아직 번역을 시작하지 않은 언어는 `미착수` 로 한 줄만 표시된다.
번역을 시작하면 자동으로 상세 점검 대상이 된다.

### 새 언어의 첫 문서를 만든 뒤에는 dev 서버를 재시작한다

**사이드바가 비어 보이는 건 버그가 아니다.** `config.js` 의 `entriesOf` 가
`readdirSync` 결과를 캐시하는데, dev 서버가 뜬 시점에 `docs/pages/<언어>/` 가
없었으면 **빈 목록이 캐시된다.** 그러면 `buildSidebar` 가 항목 0개를 내고,
VitePress 는 항목이 없는 사이드바를 아예 렌더링하지 않는다.

VitePress 는 **설정 파일**이 바뀔 때만 재시작한다. 마크다운을 새로 만드는 것으로는
캐시가 갱신되지 않으므로, 새 언어를 시작한 직후에는 `npm run docs:dev` 를 다시 띄운다.
`npm run docs:build` 는 매번 새로 계산하므로 이 영향을 받지 않는다 — 빌드에서는
사이드바가 정상이고 dev 화면에서만 비어 있으면 이 경우다.

### 자동 점검이 잡지 못하는 것

**용어 일관성(규칙 2-③)은 검사되지 않는다.** 깨진 링크도 누락된 앵커도 아니라
그냥 산문이기 때문이다. `docs/GLOSSARY.md` 와 다르게 쓴 표기는 사람이 봐야 잡힌다.

`GLOSSARY.md` 는 `ko`/`en` 대조에서 추출되어 있다. 다른 언어는 그것을 기준으로 작업한다.
